## §1 一句话骨架：先查，再答

RAG（检索增强生成）就一句话：**先把相关内容找出来，再让模型"看着这些内容"回答。**

`01` 说的"just-in-time 取资料"，落到结构上就是**两段**：

$$
\underbrace{f(\mathcal D, Q)\;\to\;P_1,\dots,P_K}_{\text{检索器：从文档集 }\mathcal D\text{ 里挑 }K\text{ 篇}}
\qquad
\underbrace{g(Q,\{P_1,\dots,P_K\})\;\to\;A}_{\text{生成器：读这 }K\text{ 篇，产出答案 }A}
$$

【slides】p15–16 就是这个框架，注意三个细节：

| 细节 | slides 的说法 |
|------|--------------|
| **$K$ 是预先定死的** | p15：$K$ is pre-defined (e.g., 100) |
| **检索器可以是"固定的老模块"** | p15：Retriever = a standard **TF-IDF** sparse model (**a fixed module**) |
| **生成器可以是零样本 LLM** | p15：Reader = 神经阅读理解模型，**或**一个零样本 LLM（ChatGPT 等） |

> **【直觉】这就是"开卷考试"**：卷子（问题 $Q$）发下来，你先去书架（$\mathcal D$）上抽 $K$ 本最相关的书（检索器），再翻着书答题（生成器）。**闭卷（纯参数）答不出的题，开卷就有机会答对。**

### 1.1 为什么"检索器可以固定、生成器换掉"这么重要

因为两段**解耦**了。你可以：换更好的生成器不动检索器；或反过来只升级检索器。**这是工程上的大便宜**——也解释了为什么 `01` §3 的"更新知识"可以用"改文档"来完成：**文档在检索器那边，不在生成器参数里。**

> **术语**：检索器（retriever）= 挑资料的那一半；生成器（generator）/读者（reader）= 读资料答题的那一半。

## §2 检索器要解决的唯一问题：**相关**

给定问题 $Q$，怎么判断哪篇文档"相关"？【slides】p17 给了三条路：

| 路线 | 代表 | 靠什么判断相关 |
|------|------|--------------|
| **词重叠** | **BM25** | 查询里的词在文档里**出现过多少、多稀罕** |
| **向量检索** | **DPR / 句向量** | 查询和文档的**稠密向量**像不像 |
| **其它神经检索** | **ColBERT** | 用模型算词级相似度（更贵、更准） |

【slides】p18 还按**快慢**排了一条谱：

```
最快：在【预计算好的向量】上算相似度
                                        ↑ 中间：混合（预建"文档索引"），如 ColBERT
最慢：用一个 LM【现算】相似度
```

> **【直觉】这就是你 408 里的"建索引 vs 全表扫描"**：预计算向量 = **建好的索引**，查的时候只做一次轻量比较（快）；用 LM 现算 = **每来一个查询就把表扫一遍**（慢但可能更准）。**"预建索引换速度"是整个检索工程的主线。**

## §3 稀疏 vs 稠密：两种"判断相关"的方式

这是本课最核心的一组对比。**先记住一句话**：

> **稀疏看"字面像不像"；稠密看"意思像不像"。**

### 3.1 稀疏检索（BM25 / TF-IDF）

**稀疏**指：每篇文档表示成一个**和词表一样长**的向量，绝大多数位置是 0（只有出现过的词非 0）。判断相关 = **数查询词在文档里出现了几次**，并按词的稀罕程度加权。

直觉三条（公式见 `04` §2）：

1. **出现次数越多越相关**（TF，词频）——但有上限，出现 100 次不比 10 次强多少（**饱和**）。
2. **越稀罕见的词越值钱**（IDF，逆文档频率）——"the" 到处都是，几乎不说明问题；"himalayas" 很少见，一出现就很大信息量。
3. **长文档要打折**（长度归一）——不然长文档只是因为词多就占便宜。

【slides】p17 点的 **BM25** 就是这三条的经典实现；**TF-IDF** 是它的前辈（少了饱和与长度归一）。

**死穴**：只认字面。查询写"**tall peak**"，文档写"**highest mountain**"——**一个词都不重合，稀疏检索打 0 分**。`03` §2 会实测到这一幕（BM25 返回 −1，即"什么都没检索到"）。

### 3.2 稠密检索（向量检索）

**稠密**指：把查询和文档都编码成一个**短的稠密向量**（如几百维，每维都非 0），判断相关 = **两个向量方向像不像**。

【slides】p19–20：用 BERT 把问题和段落各编码成向量，**打分取点积**；**DPR** 直接用问答对来训练这个编码器，**可训练的检索器显著优于传统 IR**。

**关键**：这里的"像"是**学出来的**——训练让"意思相近"的文本向量也相近，即使字面不重合。所以查询"tall peak"和文档"highest mountain"可以被打高分。`03` §2 会实测：同一个"tall/peak"查询，稠密能命中、稀疏命中不了。

> **术语**：判断两个向量像不像，最常用**余弦相似度** $\cos(u,v)=\dfrac{u^\mathsf{T}v}{\lVert u\rVert\lVert v\rVert}$——**只比方向、不管长短**（K01 里见过）。点积则是大小也管。区别与推导在 `04` §4。

### 3.3 一张对照表

| | 稀疏（BM25） | 稠密（向量） |
|---|---|---|
| 表示 | 高维、绝大多数是 0 | 短、每维都非 0 |
| 相关判据 | 字面重合 + 词稀罕度 | 向量方向（学出来的语义） |
| 强项 | 精确匹配专名/数字/代码；**快、可解释（能指出命中哪个词）** | 同义/改写/语义相近；**不要求字面重合** |
| 死穴 | 字面不重合就失手 | 需要训练/模型；**专名、数字这类"必须精确"的反而可能翻车** |
| slides 出处 | p17 | p19–20 |

### 3.4 混合：为什么工程上常用

【slides】p18 说 ColBERT 这类是"**混合（预建文档索引）**"。工程直觉很简单：

> **别二选一。** 稀疏负责"把精确匹配的捞回来"，稠密负责"把同义改写的捞回来"，两路结果合起来。这就像缓存里既放"热点精确键"也放"模糊匹配"——**保险起见两条腿走路**。

> **术语**：**混合检索（hybrid retrieval）** = 稀疏 + 稠密一起上，合并候选。

### 3.5 手算一个小例子（3 篇文档、1 个查询）

先建立手感。语料 3 篇（每篇都是一串词）：

```
D1: cat sits mat
D2: dog sits log
D3: cat dog pets
查询 Q: cat pets
```

**第一步：数每个查询词在几篇里出现（文档频率 df）。**

| 词 | 出现在 | df |
|----|--------|----|
| cat | D1, D3 | 2 |
| pets | D3 | 1 |

**第二步：罕见词权重更大。** 用一个最简的权重 $w=\ln(N/\text{df})$（$N=3$，**这是简化版，真正 BM25 见 `04` §2**）：

| 词 | 权重 |
|----|------|
| cat | $\ln(3/2)=0.405$ |
| pets | $\ln(3/1)=1.099$ |

**第三步：逐篇加权重（此处先只看"出现过没有"，不看次数、不做长度归一）。**

| 文档 | 含 cat？ | 含 pets？ | 分数 = 0.405·[cat] + 1.099·[pets] |
|------|---------|----------|-----------------------------------|
| D1 | 是 | 否 | $0.405$ |
| D2 | 否 | 否 | $0$ |
| D3 | 是 | 是 | $0.405+1.099=1.504$ |

**排名：D3 (1.504) > D1 (0.405) > D2 (0)。**

**这张小表里要读懂两件事**：

1. **"pets" 一个词顶得上 2.7 个 "cat"**（$1.099/0.405$）——因为 pets 更罕见。**这就是 IDF 的作用：罕见的词信息量大。**
2. **D2 一个字没命中，直接 0 分**——**只要字面不重合，稀疏检索就完全看不见它。这就是 `03` §2 要实测的那个死穴。**

> 真实的 BM25 在这三步上还要加两样：**TF 饱和**（同一词出现再多也有上限）与**长度归一**（长文档打折）。`04` §2 给完整式子。

## §4 分块：文档不能整篇塞进去

检索的单位通常**不是整篇文档，而是文档的一块**（chunk）。原因有两面：

- **太大**：一篇长文里只有一句相关，你却把整篇塞进上下文——**引入大量噪声**（`04` §9 讲"lost-in-the-middle"）。
- **太小**：把一句话切成半个句子——**答案被切碎，检索到了也读不懂**。

【slides】p47 从"记忆"的角度说了同一个道理：上下文窗口放不下所有东西，就算放得下，**也很难把注意力分给真正相关的事件**。

> **【直觉】这就是"缺页大小"的权衡**：页太小 → 缺页频繁、开销大；页太大 → 一次读进一堆用不上的东西。**分块大小就是一个"页大小"参数。**

### 4.1 重叠（overlap）

切块时让**相邻块共享几个句子**，叫**重叠**。动机：**防止答案正好落在切缝上**——某句话被切成两半，前半在块 A、后半在块 B，**两个块都读不全**。

> **【直觉】这就是"滑动窗口"**：网络里的滑动窗口、信号里的分帧，都靠**相邻帧重叠**来避免边界处丢信息。

`03` §3 会实测分块粒度对命中率的影响：块从 1 句加到 6 句，**hit@1 从 0/4 升到 4/4，但检索到的 token 数从 15.8 涨到 88.8**——**精度换回来的是上下文成本**。重叠也不是越多越好（实测里 3 句+重叠 2 反而让 hit@3 掉到 3/4，因为重复碎片挤掉了正确块）。

> **术语**：**分块（chunking）**、**重叠（overlap）**、**命中率（hit@k）**= 前 $k$ 个结果里有没有包含答案。

## §5 把检索结果喂给生成器

检索到 $P_1..P_K$ 之后，生成器要"**以它们为条件**"来生成——这就是**条件生成（conditioning）**：把问题 + 检索到的段落拼进一次输入，让模型据此作答。

### 5.1 "能喂几篇"是一个真问题

直觉会说："多喂几篇总没坏处。"【slides】p22–24 **明确否掉了这个直觉**：

- p23：LM **没法把注意力公平分给整个长上下文**。实验设置"1 篇相关 + 其余全不相关"：
  - 纯闭卷最好（GPT-3.5-Turbo）≈ **56%**
  - **只喂那一篇相关文档（oracle）** ≈ **88.5%**
  - → **喂对一篇就能涨 30 多个点；喂一堆无关的反而拖累。**
- p24：检索器召回率**慢慢爬到 90%**，但 **RAG 的效果在 10–20 篇后就饱和**——"再多喂"不再涨。

> **这两条是"过滤/精排"存在的理由**：既然喂太多没用、还有害，那就要**在喂之前把最相关的少数几篇挑出来**。

### 5.2 reranking：粗筛之后精排

于是有了 **reranking（重排）**：

```
第一步（粗筛，快）：用便宜的检索器从全库里捞出 top-100 候选
第二步（精排，慢）：用一个更贵的模型给这 100 个重新打分，只留 top-5 喂给生成器
```

> **【直觉】这就是"先海选、再面试"**：海选要快（能过一遍所有人），面试要准（值得多花成本，但只对少数人做）。**两阶段分工，是因为"快"和"准"在同一套打分里很难兼得**（【slides】p18 的快慢谱）。`04` §5 会给 reranking 的打分形式。

> **术语**：**reranking（重排）** = 检索出候选后用更贵的模型重新排序；**条件生成（conditioning）** = 把检索结果放进上下文让生成以它为条件。

## §6 RAG 的失败模式

RAG 不是"加了就变好"。它会以三种方式失败（这一节是把前面几条串起来，`04` §9 会给出定位顺序）：

| 失败模式 | 表现 | 根因 / 对应 |
|---|---|---|
| **① 检索错** | 相关文档根本没被捞出来（或捞错） | 稀疏/稠密各自的死穴（§3）；查询与文档用词差太远 |
| **② 上下文过长 / 淹没** | 文档在里面，但模型没看住 | 长上下文注意力不均（§5.1，56% vs 88.5%）；喂太多（10–20 篇饱和） |
| **③ 噪声 / 干扰** | 捞回来一堆无关的，把对的挤掉 | 粗筛阶段召回太宽、没做 rerank；分块太大 |

【slides】p27–28 还加了第四条容易被忽略的：

> **④ 引用幻觉**：RAG 的卖点是"能引用来源"，但**引用是模型生成的**——它可能引出一段"看起来很权威、其实对不上"的来源。实测里输出"看起来有用"，**但精确率与召回率都低**。

`03` §4 会实测最基础的对照：**同一批问题，无检索答对 1/8，有检索答对 7/8**；第 8 题（语料里根本没有的事实）**检索也救不了**——这正是失败模式①的干净例子：**没有的东西，检索不出来。**

## §7 Agent：从"说"到"做"

【slides】p29–30 把 Agent 摆出来：**LLM 核心**，外面接四块——

```
            ┌────────────────────────────────────────┐
            │                LLM 核心                 │
            └────────────────────────────────────────┘
   ┌────────────┐  ┌────────────┐  ┌────────────┐
   │ 规划与推理  │  │    记忆     │  │    工具     │
   │ReAct/CoT/  │  │episodic/   │  │检索/计算器/ │
   │Reflexion   │  │semantic/   │  │代码/搜索/   │
   │            │  │procedural  │  │读写记忆     │
   └────────────┘  └────────────┘  └────────────┘
                 ↑ observe        ↓ act
            ┌────────────────────────────────────────┐
            │       环境（外部世界）                    │
            │桌面OS/浏览器/App/游戏/机器人/数据库        │
            └────────────────────────────────────────┘
```

| 组件 | 一句话 | slides |
|---|---|---|
| **规划与推理** | 想清楚再做（ReAct / CoT / Reflexion…） | p30 |
| **记忆** | 存经历（episodic）/知识（semantic）/技能（procedural） | p30、p45 |
| **工具** | 检索、计算器、代码、搜索、读写记忆…… | p30 |
| **环境** | 动作作用的对象：OS、浏览器、机器人、数据库…… | p30 |

一句话：**Agent = 一个 LLM 核心，配上"想（规划）+ 记（记忆）+ 做（工具）"，在一个环境里循环。**

### 7.1 为什么需要"推理"

【slides】p33–34：**推理**对 LLM 是"模仿人思维过程的中间生成"，对 Agent 是**内部动作**。它有用的原因是一个朴素的观察：

> **"观察 → 行动"直接映射太难了。** 看到一个柜子、看到盐没了，直接决定"下一步做什么"很难；但如果允许模型**先想一句**（"菜要有咸味，盐没了，该找酱油，酱油在右手边柜子里"），再决定动作，就稳得多。

slides 给了两个好处：**泛化**（想过的场景能迁移）与**对齐**（想的过程人能看懂、能纠正）。

### 7.2 ReAct：观察—思考—行动

【slides】p35–36 用一个找答案的例子对比两种做法：

| 做法 | 会怎么走 |
|---|---|
| **只推理（CoT）** | "让我们一步一步想……答案是 iPhone、iPad、iPod Touch"——**全凭记忆推，可能错** |
| **推理 + 行动（ReAct）** | 想一句 → 搜一次 → 看结果 → 再想 → 再搜……**用搜索结果校正推理** |

slides p36 的 ReAct 轨迹（4 步）：

```
Thought 1: 我要搜 Apple Remote，找到它原本设计的程序
Act  1  : Search[Apple Remote]
Obs  1  : Apple Remote 于 2005 年推出……原本用于控制 Front Row……
Thought 2: 那我要搜 Front Row，看还有什么设备能控制它
Act  2  : Search[Front Row]
Obs  2  : 找不到 [Front Row]，相似项：[Front Row Seat to Earth, …]
Thought 3: 没找到，改用更精确的关键词 Front Row (software)
Act  3  : Search[Front Row (software)]
Obs  3  : Front Row 是被停用的媒体中心软件……
Thought 4: 它由 Apple Remote 或【键盘功能键】控制 → 答案就是键盘功能键
Act  4  : Finish[keyboard function keys]
```

**三步固定的节奏：`Thought`（想）→ `Act`（做）→ `Obs`（看结果）**，然后拿 `Obs` 喂回下一步的 `Thought`。**这就是 `01` §6 说的"看—想—做"循环。**

【slides】p37：**ReAct 稳定优于纯行动（Act）**；还特别点出 **CoT 的幻觉问题严重，而 ReAct 能在一定程度上缓解**——因为它是"边查边推"，不是"闭卷硬推"。

### 7.3 推理增强的几个亲戚

【slides】p38–43 列了一族：

| 方法 | 一句话 |
|---|---|
| **Self-Consistency** | 让模型走多条推理路径，**取最一致的那个答案** |
| **Reflexion** | **自我反思**：把失败的轨迹蒸馏成"自我提示"，下次别再犯 |
| **多 Agent 辩论** | 多个 Agent 互相辩论，提升推理 |
| **Orchestrator 协调** | 一个"编排者"调度多个 Agent |

### 7.4 记忆三分类

【slides】p45 按**内容**分三类（借自人的长时记忆）：

| 类型 | 存什么 | 写 / 读（p48–50） |
|---|---|---|
| **episodic（经历）** | 发生过的事 | 写=只追加的事件流；读=按启发式打分检索 |
| **semantic（知识）** | 事实/知识 | 写=对事件做 LLM 推理；读=检索 |
| **procedural（技能）** | 会做的事 | 写=代码化技能；读=向量检索 |

【slides】p51–52 的 **MemGPT** 把"记忆管理"类比成**操作系统**：用函数调用读写外部数据、**自己改自己的上下文**、自己决定何时回答用户——**性能不随上下文长度增加而下降**。

> **【直觉】记忆就是 `01` §3 的"内存/磁盘"那个类比，只是现在由 Agent 自己管**：什么时候把什么从"磁盘（外部）"搬进"内存（上下文）"、什么时候搬出去，是 Agent 的一等公民。

### 7.5 工具调用

【slides】p54–58：**工具调用（tool use）**指 Agent 生成一个"调用某工具 + 参数"的请求并拿回结果。两条代表路线：

- **Toolformer**：让 LM **自学**"调哪个 API、何时调、传什么参数、怎么把结果用回去"——做法是**只保留那些能降低后续 token 损失的调用**（p55–56）。
- **Gorilla / Toolken**：把工具当 token 或生成 {instruction, API} 对来微调（p54、p58）。

### 7.6 最简形态：一个大循环

【slides】p70–72 把编码 Agent 剥到骨头：

```
给定任务 → 反复 {
    1. LM 提出一个动作
    2. 在环境里执行它（bash / docker / python）
    3. 把输出告诉 LM
    4. 回到 1
}
```

只需要三个函数：`query_lm(messages)→response`、`parse_action(response)→action`、`execute_action(action)→output`。**"一个 AI 编码 Agent 就是一个大循环"——slides 原话就是这个意思。**
