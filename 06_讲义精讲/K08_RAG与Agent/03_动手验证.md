## §2 验证一：稀疏检索的打分与排名

**断言**（`02` §3.1）：BM25/TF-IDF 靠字面重合打分；罕见词权重大；长文档在同等命中下被打折。

**你的预期**：填一下——查询 `"highest mountain in the Himalayas"` 在 12 篇语料上，哪一篇应该最高？为什么？

**【实测】** 语料 `N=12`、平均文档长度 `avgdl=14.4167`、词表 `|V|=150`。三个查询的 top-3（文档下标, 分数）：

```
Q1 "highest mountain in the Himalayas"
   BM25  top-3: [(0, 4.8792), (1, 3.0978), (2, 1.3295)]
   TFIDF top-3: [(0, 5.1203), (1, 2.9608), (2, 1.3122)]

Q2 "programming language with simple readable syntax"
   BM25  top-3: [(6, 6.6163), (7, 2.7458), (8, 2.5008)]

Q3 "how plants use sunlight to make food"
   BM25  top-3: [(3, 2.1879), (8, 2.0578)]
```

**对账**：

- **Q1 命中 doc0（珠峰）**：查询里的 `himalayas`、`mountain`、`highest` 都在 doc0 出现，分数最高 ✅。doc1（乞力马扎罗）靠 `mountain`/`highest` 排第二，合理。
- **罕见词权重高**：`IDF('mountain')=1.3122`（12 篇里只出现在 3 篇）。**越少见，一命中越值钱**——这就是 `02` §3.5 手算表里"pets 顶 2.7 个 cat"的同一件事。
- **长文档降权**：Q2 三篇（doc6/7/8）都含 `language`，但最短的 doc7 分（2.7458）**高于更长的 doc8**（2.5008）。**同等命中，短文档不吃亏**——长度归一在起作用。

> **一处要说清的"翻车"**：Q3 里 **doc8（讲 Rust 的编程文档）排到了第 2**（2.0578）——因为查询有个词 `use`，而 doc8 正好有 "does not **use** a garbage collector"。**这是稀疏检索的典型噪声：字面撞车。** 真实系统里靠停用词表、词干化、或 rerank 压掉；本 demo 未做。

## §3 验证二：稀疏 vs 稠密——近义词查询

**断言**（`02` §3.2–§3.3）：稀疏只认字面，**字面不重合就失手**；稠密靠语义，**能命中字面不重合但意思相近的**。

**你的预期**：填一下——查询 `"how tall is the peak"`（`tall`、`peak` 都不在语料里），BM25 能找到珠峰那篇吗？稠密呢？

**【实测】** 5 个查询，三种方法的 top-1（`-1` 表示"没有任何命中"）：

```
查询                                BM25 top1   LSA top1   嵌入 top1   gold
highest mountain in the Himalayas         0           0          0      0
how tall is the peak                     -1           0          0      0
which plant makes food from light         5          11          3      3
readable coding language                  7           6          6      6
planet orbiting earth                    10          11          9      9

top-1 命中: BM25 1/5   LSA 3/5   语义嵌入 5/5
```

**对账**：

| 查询 | BM25 | 稠密嵌入 | 说明 |
|------|------|---------|------|
| `tall / peak` | **−1（完全无命中）** | **0（命中珠峰）** | **本段最干净的一幕**：`tall`/`peak` 不在语料里，稀疏一个字都碰不上；语义空间里它们和"mountain/highest"是一簇 |
| `plant…food…light` | 5（错，被 `light` 骗到"光速"那篇） | 3（对） | 语义把 `food`+`plant` 拉回光合作用 |
| `readable coding language` | 7（错，`language` 撞三篇，最短的 doc7 占便宜） | 6（对） | 语义簇把 doc6 抬上来 |
| `planet orbiting earth` | 10（错，`planet` 撞火星那篇） | 9（对，月球） | 语义簇把 moon/orbit/earth 归到一起 |

**这一屏意味着什么**：

> **稀疏和稠密是两种不同的失效方式。** BM25 只在"同一批字面"上强；一旦用户换词，它就瞎。稠密把"意思相近"编进向量方向，所以能接住换词——**代价**是它依赖一个学过语义的编码器（demo 里用**手工构造的 2 维嵌入**顶替，`00` §8.3 已声明：真实系统里这部分是 DPR/句向量学出来的）。

> ⚠️ **不要把这一屏外推**：手工嵌入是"我按语义簇摆好的"，**它的 5/5 是构造出来的**，只说明"稠密能接住不重合的字面"这个**机制**。**不能据此说"稠密总比稀疏好"** —— 稀疏在专名/数字/代码上的精确匹配反而更稳（`02` §3.3 表）。

## §4 验证三：分块粒度对命中率的影响

**断言**（`02` §4、§4.1）：块越大，答案越难被切碎（命中率高），但一次检索回来的上下文也越长（噪声多）；**重叠不是越多越好**。

**你的预期**：填一下——把每块从 1 句加到 6 句，hit@1 会怎么变？检索回来的 token 数会怎么变？

**【实测】** 4 篇长文档（每篇 6 句）、4 个查询，扫描不同"每块句数"与"重叠句数"：

```
 chunk句数   重叠   #块   平均块token  检索top3 token  hit@1  hit@3
       1    0    24        5.0          15.8     0/4    3/4
       2    0    12       10.0          31.2     2/4    4/4
       2    1    20        9.9          31.0     2/4    4/4
       3    0     8       15.0          47.2     3/4    4/4
       3    2    16       14.8          46.2     3/4    3/4
       6    0     4       30.0          88.8     4/4    4/4
```

**对账**：

1. **块越大，hit@1 越高**：1 句块 hit@1 **0/4** → 6 句块 **4/4**。**块太小会把答案切碎**（1 句块里，查询词和答案句常常不在同一块）——`02` §4"太小"那一面。
2. **代价是上下文变长**：检索 top-3 的 token 从 **15.8 → 88.8**（涨了 5.6 倍）。**命中是用"每次多读一堆无关内容"换来的**——直接连到 `02` §5.1 的"喂太多就饱和"。
3. **重叠不是越多越好**：3 句块 + 重叠 2，hit@3 **从 4/4 掉到 3/4**。为什么？**重叠制造了大量重复碎片**（块数从 8 涨到 16），这些近重复块在 top-3 里互相挤，把**正确的那一块**挤出前三。**这就是"重复内容淹没"的小型版本。**

> **一句话**：**没有一个"最好的块大小"**，只有一个"在命中率和上下文成本之间的取舍点"。工程上就是调这个参数（`05` §1、`05` §3 有踩坑条目）。

## §5 验证四：有检索 vs 无检索（toy QA）

**断言**（`01` §4、`02` §1/§6）：模型参数里没有的（实时/私有）事实，靠检索补上；**语料里也没有的事实，检索也救不了**。

**你的预期**：填一下——8 个问题里，"无检索"能答对几个？"有检索"能答对几个？

**【实测】** 8 个问题，答案都在检索库里；"无检索"模式只用一个硬记了 2 条知识的"参数记忆"来答：

```
问题                                              无检索     有检索        检索top1分
Where is Mount Everest located?                 x       OK            3.63
What is the height of Mount Everest?            x       OK            5.69
What does photosynthesis produce?               x       OK            2.19
At what temperature does water boil at sea level?x       OK            4.86
Who created Python?                             OK      OK            4.12
How often does the Moon orbit Earth?            x       OK            3.98
How far is the Sun from Earth?                  x       OK            3.34
What are the two moons of Mars called?          x       x             8.23

无检索正确: 1/8 = 12.5%
有检索正确: 7/8 = 87.5%
```

**对账**：

| 观察 | 说明 |
|------|------|
| **无检索 1/8** | 参数记忆只硬记了 2 条；"珠峰位置"只记住个大概（Nepal）但答案要求更精确，算错 ✅ |
| **有检索 7/8** | 只要检索库里有那个事实，把 top-1 段落喂给生成器就能答对 ✅ |
| **第 8 题两者都错** | 语料里**根本没有** Mars 卫星叫什么——**检索噪声再小也变不出不存在的事实**。这是 `02` §6 失败模式①（检索错/知识缺失）的干净例子 ✅ |
| **注意第 8 题的检索分最高（8.23）** | 分高 ≠ 有用。BM25 被 `moons`/`Mars` 这些词吸引，捞回了**讲火星的段落**，但那段没回答"两颗卫星叫什么"。**"检索到了"和"检索对了"是两回事** —— 这也是为什么要 rerank + 端到端评测（引 K09） |

> **一个必须说的边界**：这里"有检索 87.5%"里的**生成器是我写的一个玩具**（从检索段落里抽最相关的一句），**不是真 LLM**。它证明的是"**有检索**这条通路能把参数里没有的事实送进来"这个机制，**不代表真实 LLM 的 RAG 端到端准确率**。

## §6 验证五：Agent 的循环（ReAct 风格）

**断言**（`02` §7.2）：Agent 反复"思考→行动→观察"，**用前一步的观察决定下一步的行动**；单步做不完的任务，多步能做。

**你的预期**：填一下——"找出除 Apple Remote 外还能控制 Front Row 的设备"，只搜一次能不能拿到答案？要几步？

**【实测】** 在玩具搜索环境里跑循环（每一步：`act` 搜索 → `obs` 观察）：

```
step 1: act=Search[apple remote]          obs=The Apple Remote was introduced in 2005 to control F…
step 2: act=Search[front row]             obs=The Front Row media center program was discontinued.
step 3: act=Search[keyboard function keys] obs=Front Row can be controlled by keyboard function key…

最终答案 = 'keyboard function keys'   用了 3 步
```

**对账**：

- **3 步**：`Search[apple remote]` → 知道它控制的是 Front Row；`Search[front row]` → 知道 Front Row 是什么；`Search[keyboard function keys]` → 找到答案 ✅。
- **单步不行**：如果只用 `Search[apple remote]` 一次，拿到的段落里**没有**"keyboard function keys"。**答案在"上一步结果指向的下一步"里**——这就是 `02` §7.1 说的"'观察→行动'直接映射很难，要允许先想一步"。
- **`Obs` 决定了下一个 `Act`**：step 2 的观察（Front Row 是什么）才让你能提出 step 3 的搜索词。**这不是固定脚本，是"看结果、再决定"的循环。**

> **诚实边界**：这个循环里的"计划"（`plan = [apple remote, front row, keyboard function keys]`）是我**预写死的**，用来演示循环的**形状**；真实 Agent 的下一步动作由 LLM **当场生成**（`02` §7.6 的 `query_lm`）。**本 demo 演示的是循环骨架，不是 LLM 的决策能力。**

## §7 怎么判断"学成了"（以及它怎么接到 A4）

三个信号，**从弱到强**：

| 信号 | 怎么看 | 可信度 |

| 检索能跑通 | 给定查询能打出 top-k，排名讲得通 | 弱 |
