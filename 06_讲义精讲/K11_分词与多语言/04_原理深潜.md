## §1 BPE 的合并算法（形式化）

### 1.1 记号

| 记号 | 含义 |
|------|------|
| $D$ | 训练语料，表示成一组 (词, 频次) 对：$\{(w^{(i)}, f_i)\}$ |
| $w^{(i)}$ | 一个预分词块，表示成 **token 序列**（字节级时是字节序列） |
| $V$ | 词表（token 的集合） |
| $N$ | 目标词表大小（**上界**） |
| $\#_{ab}(w)$ | 序列 $w$ 中相邻对 $(a,b)$ 出现的次数 |

### 1.2 相邻对频次

【slides】p25 第 4a 步"Get counts of all bigrams in D"的公式化：**一个相邻对的总频次 = 它每个块内出现次数 × 该块频次，再对所有块求和**：

$$
\mathrm{cnt}(a,b)\;=\;\sum_{i} f_i\cdot \#_{ab}\big(w^{(i)}\big)
$$

**在 "Peter Piper" 语料上**（全部 $f_i=1$）：`_` 与 `p` 相邻出现在 `_picked`、`_peck`、`_pickled`、`_peppers` 四个块里，各 1 次 → $\mathrm{cnt}(\_,p)=4$。这与 `03` §2 实测的 `'_'+'p' : 4` 一致。

### 1.3 合并准则

【slides】p25 第 4b 步：**每轮选频次最高的对**，压成一个新 token：

$$
(a^\*,b^\*)\;=\;\arg\max_{(a,b)}\ \mathrm{cnt}(a,b),\qquad v_{n}=a^\*b^\*
$$

其中 $n=|V|+1$ 是新 token 的编号。然后（第 4c 步）**把 $D$ 中所有不相交的 $a^\*b^\*$ 替换成 $v_n$**。

> **注意是"不相交"**：一串 $aaaa$ 里对 $(a,a)$ 出现 2 次（重叠算 3 次：位置 1-2、2-3、3-4，其中 1-2 与 3-4 不相交），合并时按从左到右贪心扫描，得到 $[aa,aa]$ 而不是 $[a,a,a,a]$ 或 $[aa,a,a]$。本课 `code/k11_demo.py` 的 `merge_seq` 就是**从左到右贪心**。

### 1.4 并列打破（slides 没写，但必须有）

**当多个对频次并列时，选哪个？** slides **没有明说**——它只是在 $p+e$ 和 $\_+p$ 都为 4 时**选了 $\_+p$**（p30–p32）。

**这是一个实现必须自己定义的规则**，否则不同实现会产出**不同的合并列表**。常见做法：

| 规则 | 说明 |
|------|------|
| **token 字典序** | 并列时按 $(a,b)$ 的字典序取（本课采用；结果与 slides 一致） |
| 首次出现位置 | 按该对在语料里第一次出现的位置 |
| 词表编号 | 按 token 的编号 |

【实测】本课用字典序，得到 $\_+p$（因为 `'_' < 'p'`），**与 slides 的 6 次合并完全一致**（`03` §2，`一致: True`）。**这说明 slides 至少在这一例上与"字典序"相容，但不能证明 slides 用的就是字典序。**

> **工程含义**：分词器的**确定性（deterministic）**（p24 作为 BPE 的优点列出）**依赖于并列规则被显式定义**。换规则 → 换 tokenizer → 换所有 token ID → 下游全对不上。

### 1.5 编码算法（推理，【slides】p54）

训练得到 **合并列表** $M=[(a_1,b_1),\dots,(a_k,b_k)]$（**有序**）。编码一个词 $w$：

```
tokens <- 把 w 切成最小单位（字节级：UTF-8 字节）
for (a, b) in M:                    # 严格按训练顺序
    tokens <- 从左到右把 tokens 中不相交的 (a,b) 替换成 ab
return tokens
```

**注意两点**：
1. **不重新统计频次**——这是推理和训练的根本区别；
2. **顺序敏感**：$\_pi+ck\to\_pick$ 只可能在 $\_p+i\to\_pi$ 之后生效。

【实测】`_pier` → `_pi | er`（`03` §2）：先 $\_+p$ 造出 $\_p$，再 $e+r$ 造出 $er$，最后 $\_p+i$ 造出 $\_pi$。**没有一步需要"看语料"**。

### 1.6 一个 VIP 结论

BPE 是**贪心**的：每步只选当前最优的对，**不回头**。它**不是**在优化"最终词表让语料最短"这个全局目标（那是另一类字典压缩的目标）。所以：

> **BPE = 贪心字典压缩的一阶近似。** 它没有最优性保证，但**便宜、确定、够好**——这三条正是它统治前沿 LM 的原因（p24）。

## §2 WordPiece 与 Unigram：判据不同

> ⚠️ **本节 slides 只有 p23 的一句话定义**（"WordPiece 合并使数据似然最大的对""Unigram 从大词表开始丢弃"）。下面的公式是**标准结果 + 我的整理**，标注为 `【非 slides】`。

### 2.1 WordPiece：合并"似然增益最大"的对 【非 slides】

用同样的"从小到大合并"，但**打分不用频次**，用**似然比**：

$$
\mathrm{score}(a,b)\;=\;\frac{\mathrm{cnt}(ab)}{\mathrm{cnt}(a)\cdot \mathrm{cnt}(b)}
$$

每轮选 $\mathrm{score}$ 最大的对合并。

**和 BPE 的差别**：BPE 只看 $\mathrm{cnt}(ab)$；WordPiece 用**分母归一化掉单个 token 的频率**。效果：**一个本身极高频的 token（如 `e`）参与的对，不会被它的绝对频次带偏**——只看"它俩黏在一起**相对于各自独立出现**有多超出预期"。

> **【直觉】用共现打比方**：BPE 问"这对一起出现多少次"；WordPiece 问"这对一起出现的次数，比它俩各自出现次数的乘积多多少"。**后者是在排除"因为都太常见才一起出现"的假象。**（这道题的答案等价于 BERT 里能看到的 `##` 前缀子词——WordPiece 是 BERT 用的。）

### 2.2 Unigram LM：从大到小删 【非 slides】

方向反过来。假设一个**过完备**的大词表，每个 token $x$ 有权重 $p(x)$，句子 $X$ 的概率是它所有可能切分的概率之和（用 Viterbi 近似取最优切分）：

$$
P(X)=\prod_{x\in \text{seg}(X)} p(x),\qquad \mathcal{L}=\sum_{X\in D}-\log P(X)
$$

1. 用 EM 估计 $p(x)$；
2. 对每个 token 计算"**删掉它会让 $\mathcal{L}$ 涨多少**"；
3. **删掉涨幅最小的那些**（贡献最小），重复到 |V| 达标。

**和 BPE 的差别**：BPE/WordPiece **由小到大**（合并）；Unigram **由大到小**（裁剪）。Unigram 天然是**概率模型**，能给出切分的概率、也支持子词正则化。

### 2.3 SentencePiece：库，不是算法 【slides】p56

【slides】p56：SentencePiece 是一个**库**，**实现了 BPE 和 Unigram LM**，并做了两件事：
- **把空格也当作词表里的基本符号**——这样"词前空格"不用 `_` 手工标记（对比本课 §1 的 `_` 技巧）；
- 直接在**原始文本**上工作（不必先按语言规则预分词），对**无空格语言**（中/日/泰）友好。

代表使用者：T5、Llama 2、XLM-R、Gemma（p56）。

**SuperBPE**（p56）：一个"预分词课程"——先学子词，再**放开空格约束**学"superword" token，换来更小词表和更少推理算力。

## §3 词表大小与序列长度的权衡

> ⚠️ **本节是标准分析，slides 只在 p16–17 定性地提"影响序列长度和参数量"。** `【非 slides】`。

### 3.1 两组成本

设词表大小 $|V|$、嵌入维度 $d$、一段（字符数 $C$）的文本被切成 $T$ 个 token。

| 成本 | 公式 | 随 $|V|$ 增大 |
|------|------|--------------|
| **embedding 参数量** | $|V|\cdot d$（p17 的矩阵行数 = 词表） | **线性增大** |
| **输出层参数量** | 若不共享权重，再 $|V|\cdot d$ | **线性增大** |
| **序列长度** | $T$，且 $T/C$（tokens/char）随 $|V|$ 增大而**减小** | **减小** |
| **注意力算力** | $\sim T^2 d$（K04 的 $O(n^2)$） | **随 $T$ 平方减小** |
| **上下文容量** | 固定窗口能装 $T$ 个 token → 装 $T\cdot(C/T)=C$ 字符 | **同样窗口能装更多文本** |

**压缩率**是衡量"省不省"的指标：

$$
\mathrm{compression}=\frac{C}{T}=\frac{1}{\text{tokens/char}}
$$

【实测】（`03` §4）：max_merges=0（|V|=50）时 tokens/char=1.000（压缩率 1.0）；200（|V|=243）时 tokens/char=0.309（压缩率约 **3.24**）——**同样 55 字符，token 数从 55 压到 17**。

### 3.2 权衡的定量样子

**总代价 ≈ 参数代价 + 序列代价**：

$$
\underbrace{c_p\,|V| d}_{\text{embedding/输出层}}+\underbrace{c_s\,\frac{C^2}{(\text{compression})^2}\,d}_{\text{注意力}}\quad\propto\quad |V|d + \frac{C^2 d}{\text{comp}^{2}}
$$

**两股力量反向**：$|V|$ 涨 → 第一项涨、第二项降。所以**存在一个折中点**，且它**依赖于你更缺什么**：

- **显存/参数量受限**（如小模型）→ 倾向小词表；
- **上下文窗口/算力受限、要处理长文本** → 倾向大词表（同样窗口装更多字）。

### 3.3 边际收益递减与饱和

【实测】`03` §4：token 数 55 → 28 → 18 → 17，**在 200 次合并后饱和**（本课语料的不同词有限）。真实 tokenizer 的曲线也**先陡后平**：最该被合并的高频组合先被吃掉，后加的 token 只处理长尾。

> **【直觉】这就是"熵编码"的老规律**：最常出现的组合先编码，收益最大；越到后面，能省的越少。**词表不是越大越好，而是要匹配语料的无空格/长尾结构。**

### 3.4 一个常被忽略的耦合：词表和语言绑定

词表是在**某个语料**上学出来的（§1）。所以"词表大小"这个旋钮**不是一个中立的超参**——它把**语料的语言分布**固化进了模型输入层（`03` §3 的 0% vs 0.60% 实测就是这个）。

## §4 fertility 与多语言不均衡

> ⚠️ **fertility 的定义在 slides p71 有；下面的分解与因果链是我的整理。** 分节标注。

### 4.1 定义 【slides】p71

**subword fertility = 每词平均产生的子词 token 数**：

$$
\mathrm{F}=\frac{1}{N_{\text{words}}}\sum_{i=1}^{N_{\text{words}}}\ \#\text{tokens}(w_i)
$$

（"词"通常按空格/分词器口径数。对无空格语言，"每词"这一口径本身就要先定，这也是 p56 的痛点之一。）

### 4.2 为什么低资源语言 fertility 高 【非 slides】

回到 §1.3 的合并准则：BPE 选 $\arg\max \mathrm{cnt}(a,b)$，而 $\mathrm{cnt}$ 是**语料加权频次**。设语言 $\ell$ 在语料里占比 $\pi_\ell$：

- $\pi_\ell$ 高（如英文 40–45%，p64）→ 它的相邻对频次高 → **优先被合并** → 它的词先变成整 token → **fertility 低**；
- $\pi_\ell$ 低（如 <0.01%，p64）→ 它的对**永远排不上号** → 只能保留字节 → **fertility 高**。

**本课的最小实验**（`03` §3）：中文占比 0.60% → 0.500 tokens/char；占比 0% → 3.000 tokens/char（= 3 字节/字）。

### 4.3 为什么 fertility 高是坏事 【非 slides】

token 数是**计费和算力的基本单位**（p71）：

| 后果 | 机制 |
|------|------|
| **更贵** | 注意力 $\sim T^2$；同一个意思 $T$ 越大越贵。API 按 token 计费 → **非英语用户多付**（Ahia et al., 2023） |
| **更少上下文** | 固定窗口 8192 token，英文能装 ~26k 字符，高 fertility 语言只能装 ~2.7k 字符（按 0.309 vs 3.0 tokens/char 估算） |
| **更差的下游性能** | 【slides】p71：fertility 与下游性能**强负相关**——切得碎，模型更难从碎片拼出语义 |
| **更难对齐** | 同一意思在不同语言 token 数不同 → 跨语言迁移/对齐更难（p67–69：多语言诅咒） |

### 4.4 完整因果链（本课的落点）

```
语料占比低
   → 相邻对频次低
   → BPE 合并预算被高频语言吃掉
   → 低资源语言词被切碎（fertility 高）
   → 序列长、算力贵、上下文少、性能差
   → 在模型训练之前就发生（p15），后面每一步放大
```

【slides】p71 的两个量级数字：**分词可能和预训练数据量同等重要**（Rust et al., 2021）；**等义文本 token 长度差最高 15 倍**（Petrov et al., 2023）。

### 4.5 三条缓解方向（slides 给的线索）

| 方向 | slides | 机制 |
|------|--------|------|
| **加大词表覆盖** | p68：XLM-V 扩到 1M token（4× XLM-R） | 给低资源语言更多槽位；代价是效率 |
| **提高词表重叠** | p68：重叠 > 不重叠，"假朋友"也帮 | 共享子词促进跨语言迁移 |
| **回到字节/字符级** | p72–75：CANINE 覆盖全 Unicode，能处理没见过的语言；MrT5 用删除门压缩 | 交换：无 OOV、鲁棒，但序列长（用架构创新换回来） |

## §5 字节级回退：为什么无 OOV、代价是什么

> ⚠️ **slides p21 给了 `地`=3 字节、`😀`=4 字节；下面的 UTF-8 机制是标准事实。** `【非 slides】`。

### 5.1 机制

**UTF-8 是自同步的变长编码**：ASCII 1 字节、拉丁/希腊等 2 字节、常用汉字 3 字节、emoji 等 4 字节。**任何 Unicode 字符**都能编码成 1–4 个字节。

字节级 BPE 的初始词表就是 **256 个字节值**（或语料中出现的那些字节，本课实测初始 |V|=50，`03` §3）。因此：

$$
\forall\ \text{字符串}\ s,\quad s\ \text{总能被切成字节序列}\ \Rightarrow\ \text{无 OOV}
$$

**编码时，若某个字符的字节组合没被任何合并规则命中，它就保持为单个字节**——这就是"回退"。

【实测】`地球 → 5 tokens`（`地` 2 token、`球` 3 token），`😀 → 4 tokens`（`03` §5）。

### 5.2 代价

| 后果 | 说明 |
|------|------|
| **序列变长** | 每个未见字符 = 1–4 个 byte-token（RETRO：中文 3×、emoji 4×） |
| **字符级任务仍难** | 见到的仍是**子词块**，不是字符——数 `r`、反转字符串仍难（p59）；字节级只是让"没有字符是完全未知的"，不等于给了字符级接口 |
| **信息被摊平** | 一个汉字被拆成 3 个无语义字节，模型要自己学会"这 3 个字节是一个字" |

### 5.3 两种"字节级"不是一回事

| 名称 | 切分单位 | 代表 |
|------|---------|------|
| **字节级 BPE**（"tokenizer-free" 的一种夸张说法） | 仍产出**合并后的子词 token**，只是起点是字节 | GPT-2（p24） |
| **纯字节/字符模型** | **不用 tokenizer**，直接吃字节 | ByT5、CANINE、Charformer（p21） |

【slides】p21 自己也加了个 aside："should we call these tokenizer-free?"——**名字有争议**。

【slides】p75 给的未来方向：**潜在分词（latent tokenization）**——让模型在**架构里**学"有意义的单位"，把"分词"从预处理挪回模型内部。MrT5 的**删除门**就是这类做法：动态缩短序列、**学到语言特定的压缩**（p73）。

## §6 一个可以带走的判断模式

把 §1–§5 收成一条可复用的思路：

> **任何"把可变长输入变成定长符号序列"的系统，都在这三件事上做同样的权衡**：
> 1. **起点粒度**（字节 / 字符 / 子词 / 词）；
> 2. **合并判据**（频次 / 似然 / 概率）；
> 3. **预算分配**（词表上限、语料配比）。
>
> **BPE 选了"字节 + 频次 + 贪心"**，所以它**便宜、确定、可复现**——但也把"语料分布的不平等"直接编码进了词表（§4）。换成 WordPiece/Unigram 只改第 2 项，**改不了第 1/3 项造成的语言不均衡**。
