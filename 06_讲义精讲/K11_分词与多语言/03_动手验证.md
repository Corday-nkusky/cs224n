## §2 验证一：复现 slides 的 BPE 全过程

**断言**（`02` §4、`00` §3.E、【slides】p25–p53）：从字节起，每次合并**最高频**的相邻对；频次并列时 slides 选了 `_+p`。

**你的预期**：初始词表有几个字符？`_+p` 和 `p+e` 的频次各是多少、谁先被合并？

**【实测】语料与初始状态**：

```
语料（预分词后；'_' 表示词前空格）:
  Peter | _Piper | _picked | _a | _peck | _of | _pickled | _peppers
初始词表（D 中出现的单个字符）:
  ['P','_','a','c','d','e','f','i','k','l','o','p','r','s','t']   （15 个）
初始相邻对频次（降序，节选）:
  '_' + 'p' : 4
  'p' + 'e' : 4
  'c' + 'k' : 3
  'e' + 'r' : 3
  'e' + 'd' : 2
  'i' + 'c' : 2
  'p' + 'i' : 2
```

**对账**：与 slides p28（15 个字符）、p30（频次表）**逐项一致** ✅。

**六次合并**：

```
merge  1: '_'  + 'p'  -> '_p'    频次=4   |V|=16
merge  2: 'c'  + 'k'  -> 'ck'    频次=3   |V|=17
merge  3: 'e'  + 'r'  -> 'er'    频次=3   |V|=18
merge  4: '_p' + 'e'  -> '_pe'   频次=2   |V|=19
merge  5: '_p' + 'i'  -> '_pi'   频次=2   |V|=20
merge  6: '_pi'+ 'ck' -> '_pick' 频次=2   |V|=21
```

**对账**（脚本自己做的逐项比对）：

```
slides : [('_','p','_p'), ('c','k','ck'), ('e','r','er'), ('_p','e','_pe'), ('_p','i','_pi'), ('_pi','ck','_pick')]
实测   : [('_','p','_p'), ('c','k','ck'), ('e','r','er'), ('_p','e','_pe'), ('_p','i','_pi'), ('_pi','ck','_pick')]
一致   : True
```

**这一屏意味着什么**：

1. **`_+p` 与 `p+e` 频次并列（都是 4）**。slides 选了 `_+p`。本实现用"**频次并列时按 token 字典序**"打破，得到的也是 `_+p`（`'_' < 'p'`）——**并列规则是 BPE 必须显式定义的一件事**，否则实现之间结果会不一样（`04` §1 展开）。
2. **每次合并后频次表会变**（因为语料被改写），所以是"**一遍遍重数**"，不是一开始数一次。merge 6 的 `_pi+ck` 只有在 merge 5 造出 `_pi` 之后才可能存在——**顺序不能乱**。

**推理（编码新词）**：

```
'_pier' -> _pi | er   （2 tokens）
```

**对账**：与 slides p54 的 `Merge1: _p i e r → Merge3: _p i er → Merge5: _pi er` 一致 ✅。**推理没有重新统计频次**——只把 6 条规则按顺序套了一遍。

> **这条对理解了 tiktoken 很重要**：真实 tokenizer 的推理就是"查合并表"，所以**极快、极确定**（p24 的 "deterministic"）。不确定性全在**训练**那一步（选哪对、怎么打破并列）。

## §3 验证二：多语言不均衡

**断言**（`02` §8、【slides】p62/p64/p71）：训练语料以英文为主时，同一句话的中文会被切成更多 token。

**你的预期**：中文句 `我们看着银河`（6 个字符）会变成几个 token？tokens/char 会比英文高几倍？

**【实测】语料规模**：

```
英文 108 词 / 总频次 4472；中文 7 词 / 总频次 27
中文数据占比 = 0.60%
初始 |V| = 语料中出现的不同字节数 = 50
训练 200 次合并后 词表大小 |V| = 243
```

**同一个分词器（双语，|V|=243）下**：

```
英文：'we looked at the milky way'
  tokens=6  chars=21  tokens/char=0.286  tokens/word=1.000
  切分: we | looked | at | the | milky | way

中文：'我们看着银河'
  tokens=3  chars=6  tokens/char=0.500
  切分: 我们 | 看着 | 银河

→ 同一分词器下，中文的 tokens/char 是英文的 1.8 倍
```

**对账**：中文每个"词"被合成 1 个 token（`我们`/`看着`/`银河`），但**单位字符的 token 数仍是英文的 1.8 倍** ✅。原因是英文一个 token 平均覆盖 3.5 个字符（21/6），中文一个 token 只覆盖 2 个字符。

**对照：如果分词器只见过英文**：

```
只喂英文语料训练的分词器（|V|=182，中文数据占比 0%）
  同一个中文句 '我们看着银河':
    tokens=18  chars=6  tokens/char=3.000
    切分: e6 | 88 | 91 | e4 | bb | ac | e7 | 9c | 8b | e7 | 9d | 80 | e9 | 93 | b6 | e6 | b2 | b3

→ 中文数据占比从 0% 提到 0.60%，中文 tokens/char 从 3.000 降到 0.500（降 6.0 倍）
```

**对账**：**每个中文字 = 3 个字节 = 3 个 token**（18 = 6×3）✅。

**两屏合起来意味着什么**：

| 场景 | 中文 tokens/char | 相对英文 |
|------|------------------|---------|
| 分词器完全没见过中文（0% 数据） | **3.000** | 10.5 倍 |
| 中文只占 0.60% | 0.500 | 1.8 倍 |
| 英文（对照） | 0.286 | 1 倍 |

> **这就是"低资源代价"的完整机制**：token 数直接决定**你付多少算力、占多少上下文、API 收你多少钱**（p71）。而它**在模型训练之前就发生了**（p15）。`04` §4 会把它写成 fertility 的公式。

## §4 验证三：词表大小 vs 序列长度

**断言**（`02` §9、【slides】p16–17）：词表越大 → 每个词越可能被合成一个 token → 序列越短。

**你的预期**：把词表上限从 0 提到 800，token 数会一直降下去吗？还是降到某个值就停？

**【实测】**（测试句 55 字符 / 17 词）：

| max_merges | \|V\| | tokens | tok/word | tok/char |
|-----------:|------:|-------:|---------:|---------:|
| 0 | 50 | 55 | 3.235 | 1.000 |
| 50 | 100 | 28 | 1.647 | 0.509 |
| 100 | 150 | 18 | 1.059 | 0.327 |
| 200 | 243 | 17 | 1.000 | 0.309 |
| 400 | 243 | 17 | 1.000 | 0.309 |
| 800 | 243 | 17 | 1.000 | 0.309 |

**对账**：token 数 **单调不增**，从 55 降到 17（**压掉 69%**）✅。但**在 200 次合并后饱和**：|V| 不再涨（243），token 数停在 17（= 词数，每个词都成 1 个 token）。

**为什么饱和**：本课语料的**不同词只有 108 个**，全部合成整词后，没有新组合可合并了。**真实 tokenizer 不会这么早饱和**（语料大、词形多），但"**边际收益递减**"这条规律一样：越往后，每加一个 token 省下的序列越少。

**两屏合起来意味着什么**：

> **词表大小是一组权衡**：词表大 → 序列短（省注意力/省上下文），但 **embedding 矩阵 $|V|\times d$ 更大**，softmax 也更大（p16–17）。这不是"越大越好"。

## §5 验证四：字节级回退、OOV 与拼写

**断言**（`02` §6/§7、【slides】p21/p59）：字节级 BPE 没有 OOV，但没见过的字符会被切成字节；改一个字符会移动合并边界。

**你的预期**：`地球`（2 字符）会变成几个 token？`important` 和 `impoooortant` 的 token 数一样吗？

**【实测】**（用 §3 的双语分词器，|V|=243）：

```
           'milky' ->   1 tokens: milky
       'important' ->   6 tokens: im | p | or | t | an | t
       'importent' ->   6 tokens: im | p | or | t | e | nt
    'impoooortant' ->   9 tokens: im | p | o | o | o | or | t | an | t
              '地球' ->   5 tokens: e59c | b0 | e7 | 90 | 83
               '😀' ->   4 tokens: f0 | 9f | 98 | 80
```

**对账**：

| 观察 | 数字 | 说明 |
|------|------|------|
| 训练里见过的整词 | `milky → 1` | 直接命中整词 token |
| 没见过的英文词 | `important → 6` | 拆成训练里学到的子词（`im`/`an`/`or`…） |
| 改一个字符 | `importent → 6`，但**切法不同**（`e \| nt` vs `an \| t`） | 合并边界移动了 |
| 插一个重复字符 | `impoooortant → 9` | 序列变长 |
| 没见过的中文 | `地球 → 5` | `地`=2 token、`球`=3 token（≈ 3 字节/字） |
| emoji | `😀 → 4` | 正好 4 个字节 |

**这一屏意味着什么**：

1. **"无 OOV"是字节级的功劳**：`地球`、`😀` 都不在训练语料里，但都**编得出来**（退回字节）。**代价是被切碎**——这正是 §3 里 3.000 tokens/char 的来源。
2. **对拼写任务不利**：模型看到的是子词块，不是字符（【slides】p59：GPT-2 `strawberry → ["str","aw","berry"]`，数不出 r 的个数）。**本课没有字符级访问能力**时，"数某个字母出现几次""反转字符串"这类任务就是难的。
3. **鲁棒性差**：`important → importent → impoooortant` 三条串产出三套不同切分。**一个字符的改动会移动所有 BPE 合并边界**（p59）。

## §6 怎么判断"学成了"（以及它怎么接到你的方向）

三个信号，**从弱到强**：

| 信号 | 怎么看 | 可信度 |
|------|--------|--------|
| 能复述 BPE 四步 | 口述"从字节起、合并最高频相邻对、重数、替换" | 弱 |
| **能复现合并序列** | 在 "Peter Piper" 上算出前 3 次合并的对与频次 | 中 —— **本课核心判据** |
| 能解释三个数字 | tokens/char 的 1.8×/6×、词表饱和、字节回退 | 强 |

**和你的方向（方言 ASR 低数据适配）的对应**：

| 本课验证 | 对你的意义 |
|---------|-----------|
| §3 中文 0.60% 占比就带来 1.8× token | 你的方言语料占比更低，**序列会先被拉长**——训练成本、上下文占用都在 tokenizer 这一步涨 |
| §3 0% → 3.000 tokens/char | 若分词器训练时完全没喂方言文本，**方言字会被拆成字节**，模型学到的"字"没有整体性 |
| §4 词表饱和 | 单纯加词表上限不一定救低资源语言——**合并预算被高频语言吃掉了**（`04` §4） |
| §5 字节回退切碎 + 拼写敏感 | 方言的口语化拼写/异体字会**反复改变切分**，加剧数据稀疏 |
| §2 推理=查表 | 你**不能**在微调时才改 tokenizer；要改就重训 tokenizer + 重新对齐 embedding |
