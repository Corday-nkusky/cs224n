# K11 · 01 为什么需要它

> **进这一篇之前你能说出什么**：K01–K10 的一整套——词向量是查表得到的向量（K01）、模型是"输入 → 一堆矩阵运算 → 输出"（K02）、Transformer 的输入是一串向量（K04）、模型有上下文窗口上限。
> **这一篇回答什么**：模型明明只吃数字，**文本是怎么变成数字的**？"按空格切词"这个最自然的做法，为什么会把模型坑死？切得再细一点（按字符）又有什么代价？
> **读完你应该能说出什么**：
> 1. 分词是**训练之前**就把"模型能看到什么"定死的一步
> 2. 按词切有两条死因：**词表爆炸/长尾** + **未登录词**
> 3. 按字符切解决了覆盖问题，却把**序列长度**拉爆——所以要一个折中

**这一篇不引入本知识点的新术语（token / tokenizer / BPE / 子词都留到 `02`），也不写代码、不推公式。** 打比方只用你已经会的 CS 知识（字符编码、压缩、哈希表）。

---

## §1 问题：模型读不了字符串

先回忆一件你已经知道的事：**语言模型的输入是一个向量序列**（K04 的 Transformer，K03 的 RNN，都一样）。

但现实里你手上拿到的是**一串字符**：

```
We looked at the Milky Way.
```

模型没法把这串字符直接送进矩阵乘法。它需要一个映射：**字符串 → 一串整数 ID → 一串向量**（【slides】p9 的原话：*"Models can't just read raw text → we need a mapping from strings to sequences of embeddings"*）。

【slides】p8 把这件事拆成三个词：

| 词 | 指什么 |
|----|-------|
| **token** | 语言模型处理的基本单位（**注意：不一定是"词"**） |
| **tokenizer** | 在"文本 ↔ token 序列"之间翻译的程序 |
| **词表（vocabulary）** | 所有已知 token 的集合 |

slides 给了一个具体例子（p8）：`We looked at the Milky Way.` 经过 tokenizer 变成

```
[2167, 10802, 540, 290, 10282, 5781, 0]
```

这些整数再去查一张 embedding 矩阵，每个变成一个向量（p11–14）。

> **【直觉】用你 408 里的东西打比方：这就是一张"字符串 → 主键"的映射表。**
> 你把一堆字符串塞进来，它回给你一堆整数 ID；这些 ID 再去"数据库"（embedding 矩阵）里查出对应的行（向量）。**和编译器把标识符塞进符号表、数据库把行按主键存取，是同一类操作。**
>
> **关键差别**：数据库的键是**你定的**；而这里"文本该被切成哪些字符串"，是**要提前用算法定下来的**——**这就是这一课的全部麻烦。**

> **术语预告**：上面这套"把文本切成单位、映射成 ID"的机制，叫**分词（tokenization）**。`02` 正式展开。

---

## §2 第一件要知道的事：分词在模型训练**之前**就发生了

【slides】p15 一句话点破：

> **"Tokenization is typically a preprocessing step, not part of the core LM."**

翻成人话：**分词不是模型学的**，是你事先选好、固定死的。模型从第一步起，看到的就只是"已经被切好的那串 ID"——**切法变了，模型看到的世界就变了**。

【slides】p16–17 又补一句：分词同时决定两件事——
- **序列长度**：切得越碎，序列越长（越费算力、越占上下文窗口）；
- **参数量**：词表越大，那张 embedding 矩阵越大。

> **【直觉】把它想成"喂给模型的数据在入库前的分表策略"。** 分表方案一旦定了，后面所有查询（训练、推理）的代价都被它锁死。**你不能训练到一半再改切法——那等于换了一套主键，模型学过的行全对不上了。**

所以这一课不是"一个预处理小细节"，而是**在模型还没开始学之前，就替它决定了成本和能力边界**。这也是为什么它对"低资源语言的公平性"影响巨大（`00` §3.G）。

## §3 第一代方案：按词切——两条死因

最自然的想法：**一个词一个 token**。按空格切，词表取语料里最高频的 V 个词。

【slides】p18 说它有一个真优点：**语义上有意义的单位**——"一个 embedding ≈ 一个可解释的意思"。

但它有两条硬伤。

### 3.1 死因①：词太多，而且永远在长

【slides】p19 原话：**"There are too many words! Vocab can be huge."**

原因是 **Zipf 定律**：一个词的频次与它的**频次排名成反比**。翻译成人话就是——

```
极少数词（the / of / and）出现几百万次；
绝大多数词只出现一两次。
```

这叫**长尾**。你想要的词表大小是有限的，但语料里的**不同词**会一直涨。更糟的是【slides】p19：**语言一直在变**——Merriam-Webster 第 12 版一次就新增了 5k 词（包括 "rizz"）。

> **【直觉】哈希表 vs 数组。** 按词切等于给**每个出现过的字符串**都开一个固定槽位。短文本还行，真实语料里"不同字符串"的数量会爆炸——**这正是哈希表要解决的问题，而词级分词反着来，硬要给每个 key 一个永久槽位。**

### 3.2 死因②：没见过的词怎么办（OOV）

就算你截断了词表，**测试时一定会遇到词表里没有的词**——新词、错拼、专有名词、别的语言。这就是 **OOV（未登录词）**（【slides】p20）。

slides 列了两个补丁：

| 补丁 | 做法 | 后果 |
|------|------|------|
| **① 规则预处理** | 用正则/规则把文本规范化：`importaNt → important`、`ESPRESSSOOO → ESPRESSO` | 规则永远补不完，且很脆 |
| **② 一个 `UNK` 代表所有未知词** | 词表外的一切都映射成 `UNK` | **大量词被压成同一个符号**，信息丢光 |

> **【直觉】`UNK` 就像"查不到就返回 NULL"。** 你写 `SELECT * WHERE key='xx'` 查不到，返回一个 NULL——程序不崩，但**所有查不到的行在你这儿都长一个样**，你还分不出来它们是哪些。模型看到一串 `UNK` 时，就是这种感觉。

## §4 第二代方案：按字符/字节切——覆盖解决了，长度爆了

既然"词"这个粒度抓不住，那就**退到最小粒度**：一个字符一个 token。

【slides】p21 先纠正一个容易忽略的点：**字节 ≠ 字符**。
- `😀` = **1 个字符，4 个字节**；
- `地` = **1 个字符，3 个字节**。

**优点**（p21）：词表极小（就几十~几百个）、**完全覆盖输入（没有 OOV！）**、能直接看到拼写。

**缺点**（p21）：**"Really long sequences…"**。

这条缺点有多致命，用你自己的 K04 知识就能算：Transformer 的注意力是 **$O(n^2)$**（K04 的"新代价"）。序列从"20 个词"变成"100 个字符"，注意力计算量涨的是 **25 倍**。

> **【直觉】用字符编码打比方。** 你想"看到一个字符就知道它是什么"，最保险的做法是**把每个字符都编成一个码点**（`地 → 3 字节`）。**覆盖是 100% 了，但表示变长了。** 反过来，把常见整词压成一个符号（像给高频串一个短码），序列短，但"没在字典里的串"就编不出来了。
>
> **这就是压缩算法里的经典权衡：字典越大 → 每组数据的码越短，但字典本身越大、覆盖越难。** 分词要的，就是这个权衡的一个好点。

> **术语预告**：英文还可以按"词的一部分"切（`looked → look + ed`），中文每个字本身就是一个 token。这个"比词细、比字符粗"的粒度叫**子词（subword）**。`02` 展开。

## §5 折中：子词

把 §3 和 §4 的诉求摆在一起：

| 想要 | 词级给不给 | 字符级给不给 |
|------|-----------|-------------|
| 语义上有意义的单位 | ✅ | ❌（一个字符没意义） |
| 词表可控、不爆炸 | ❌（长尾） | ✅（很小） |
| 覆盖所有输入、无 OOV | ❌ | ✅ |
| 序列别太长 | ✅ | ❌ |

**没有一边能全占。** 于是要一个中间粒度：**token 是"词或词的一部分"**（【slides】p22）。

【slides】p22 的关键一句：词表**不是人工定，而是"用数据 + 算法"从语料统计里学出来**的。代价是——**大多数切分和语言学不对齐**（比如 `Milky`、`looked` 的切法，人不会这么切，但统计会）。

【slides】p22 给的例子也很直观：同一句话里，有的词被切成一个 token（`We'd`），有的被切成几块（`Milky`、`looked`）。

> **【直觉】回到压缩算法。** 子词分词就是一个**自动学出来的字典压缩器**：字典条目不是人工选的，而是"哪种切法能让整篇语料最短"选出来的。**出现得多、能省字的组合，被合成一个符号。** `02` 手算的时候你会亲眼看到这个过程——它就是**反复挑最高频的相邻两个符号，合成一个**（【slides】p25）。

> **术语预告**：这个"从字节开始、反复合并最高频相邻对"的算法叫 **BPE**。`02` 手算，`04` 讲透。

## §6 没有它会怎样

把这一课要解决的问题摆齐：

| 如果没有…… | 后果 |
|---|---|
| **一种可靠的"文本 → 单位 → ID"映射** | 模型根本读不了文本，整套 NLP 无从谈起（§1） |
| **比词细的粒度** | OOV 无处不在，长尾词全变 `UNK`（§3.2） |
| **比字符粗的粒度** | 序列长度被拉爆，$O(n^2)$ 的注意力直接算不动（§4） |
| **"在训练前定死、且尽量通用"的设计** | 低资源语言/方言在还没训练时就被不公平对待（§2、`00` §3.G） |

**最后一条是这一课与你方向相关的落点**：分词不均衡不是"训练时的调参问题"，而是**在模型学任何东西之前就写进输入分布里的结构性偏差**。它会在后面每一步放大。
