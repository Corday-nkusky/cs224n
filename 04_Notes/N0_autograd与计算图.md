# N0 · Autograd 与计算图：机制层面到底发生了什么

> 原则声明：本文档区分三种口径——**论文/教材口径**、**PyTorch 实现口径**、**工程经验**。凡简化处明确标注。

## 1. 计算图是什么

你写的每行张量运算，PyTorch 都在后台记一张"操作图"：节点是张量，边是运算。这不是比喻——**每次前向运算时，每个生成的中间张量都持有 `grad_fn` 指针，指向产生它的那个运算**。整张图就是靠这些指针串起来的链表结构，随代码执行动态生长（所以叫**动态图**，区别于 TensorFlow 1.x 的先定义后执行的静态图）。

## 2. `backward()` 具体做了什么

`loss.backward()` 触发一次**反向遍历**：从 `loss` 这个节点出发，沿 `grad_fn` 指针逆向走完整张图，每到一个运算节点就调用该运算**预先注册好的求导法则**（每个算子都实现了自己的 `backward`，比如加法的反向是恒等分发、乘法的反向是"乘上对方"），把梯度逐段往回传。

关键事实：

- **梯度只写到"叶子"张量的 `.grad` 属性里**。叶子 = 你自己创建且 `requires_grad=True` 的张量（典型就是 `nn.Parameter`）。中间张量的梯度默认**算完即丢**（除非显式 `retain_grad()`）——省内存，也解释了为什么你在中间变量上看不到 `.grad`。
- **`backward()` 只能从标量调用**。默认参数 `gradient=None` 的语义是"假设最外层对 loss 求导的链式系数是 1"，这只对标量良定义。如果 loss 是向量，你必须显式传入一个同形状的"上游梯度"张量 `v`，此时算的是 `vᵀ·J`（Jacobian-向量积）——这是有明确定义的数学操作，不是黑魔法。

## 3. `optimizer.step()` 与 `zero_grad()`

- `step()`：遍历 optimizer 里登记的参数组，对每个参数执行 `p.data -= lr * p.grad`（以 SGD 为例；Adam 换的是更新量的算法，写入位置不变）。**它只改参数数据，不碰计算图。**
- `zero_grad()`：把所有登记参数的 `.grad` **清零而不是清空**。为什么必须调：PyTorch 的设计是**梯度累加**——`backward()` 是 `+=` 语义。这个设计本身有正经用途（大 batch 拆多次前向再统一 step 的**梯度累积**技巧），但日常训练忘调它，效果等于学习率随 batch 数放大，loss 曲线会莫名校正——**遇到"曲线漂移"先查这个**。

## 4. `requires_grad` 与 `no_grad`

- `requires_grad=True` 声明"这个张量参与求导"。张量运算的输出是否可导，由输入的"是否需要梯度"**传播**决定——这就是为什么冻结模型时把 `param.requires_grad = False` 一刀切下去，上游整段就自动不建图了（T4 微调要用）。
- `torch.no_grad()`：上下文内**完全不建图**。推理时用它的省的不是"梯度存储"这么简单——是连前向的 `grad_fn` 记账都省了，内存和速度都受益。

## 5. 与 T2 的关系

T2 里你在 A2 手写的 backprop，就是本文档 §2 中"每个算子注册的求导法则 + 链式法则组合"的展开。autograd 没有任何超过链式法则的东西——它的价值是**把这 bureaucratic 的机械过程自动化了**。T2 做完你应该能用本文档的语言，向别人解释 `w1 → h1 → loss` 两步图里每个 `.grad_fn` 是谁、梯度怎么流。
